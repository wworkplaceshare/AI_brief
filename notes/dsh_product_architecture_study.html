01. 总判断：DSH 是 Agent 产品底座，不只是 coding agent

如果把 DSH 当作单一 CLI agent，它会显得过重；如果产品目标是“同一套 runtime 同时服务 Web、Headless、SDK、ACP、Desktop，并允许不同 agent preset、插件、后端、权限和长期会话”，它的大部分设计就有了产品理由。

三个真正支付复杂度的产品承诺：① 同一 runtime 支持多种产品 surface；② agent 能对真实世界产生副作用；③ 任务寿命可以长于进程寿命，并且要能恢复、解释、继续。你的产品如果缺少其中两项，就不要照搬整套 DSH。
必须学

Runtime / Surface 分离

业务能力不能属于 Web、CLI 或 SDK；入口只负责 transport / interaction。

必须学

状态 / 副作用边界

取消、恢复、审批、工具执行、持久化是 agent runtime 的核心语义。

按规模决定

Everything is a Plugin

原则有价值；是否把几乎所有东西都做成 Cordis plugin，要看产品线和生态规模。

读源码时始终沿这条链走，不从“某个 pattern 很漂亮”开始。

02. 用户模型：Who 与 How 必须分开

“终端用户 / Webhook / SDK / 插件作者”不是同一个分类维度。更适合产品设计的拆法是先分角色，再分使用方式。

Who真正的 Job最在意什么典型 How
Interactive Developer / Researcher把 workspace 中的任务交给 agent，并持续 steering起步快、可见、可取消、权限可控、上下文连续Web / Desktop / CLI
Automation Owner无人值守完成任务确定退出、无 UI 依赖、重试/超时、机器可读状态Headless / Schedule / Webhook / CI
Application Integrator把 agent runtime 嵌入自己的产品稳定协议、生命周期、隔离、可裁剪SDK / ACP / JSON-RPC
Extension Developer增加 tool/provider/policy/backend，不 fork 主项目扩展点、依赖、生命周期、兼容、分发Plugin / Bundle / Preset
Operator / Auditor部署、排障、升级、追责日志、provenance、权限、持久化、迁移Session storage / diagnostics
关键：同一个人可以切换 How。开发者白天 Web 交互，晚上把同类任务交给 Headless。真正要共享的是 runtime 语义，而不是 UI。

03. 典型用户旅程：每条旅程都会逼出一组架构要求

A. Interactive

选 workspace → 给任务 → agent 读写文件、跑命令 → 中途 steering → 审批 → 看结果。

压力：workspace 边界、实时流、inbox、取消、权限、上下文增长。

B. Headless

无人值守执行；失败不能卡在 UI；进程必须明确结束。

压力：headless policy、timeout、durable state、无 UI 依赖。

C. SDK / ACP

自己的产品拥有 UI，DSH 只是子进程 runtime。

压力：transport 与 runtime 解耦；协议化生命周期；独立 home/workspace。

D. Long-running / Resume

进程崩溃或重启后能继续；历史不能靠内存对象。

压力：append-only log、checkpoint、格式迁移、interrupted turn repair。

E. Plugin ecosystem

第三方增加能力；启停/卸载后不留下监听器；provider 可替换。

压力：DI、生命周期、scope、config composition、包管理。

F. Operator

回答“模型当时看到什么、调用了什么、谁批准了什么”。

压力：model-visible state 与 durable state 对齐；request metadata；diagnostics。

05. 核心 Runtime：真正应该先读的不是 Cordis，而是一轮任务怎么跑

官方架构把一个 step 定义为一次模型请求加其工具执行；一个 turn 可以包含多个 step。理解这条数据流以后，再看 plugin 才不会迷路。

这是 DSH 最值得先掌握的数据流。Plugin system 是围绕这条流提供扩展点。
值得抄：把 durable facts 和 live control plane 分开。不要把 WebSocket stream 当历史，也不要把历史数据库当实时控制通道。

Source: docs/architecture.zh.md → 轮次流程、事件、会话日志；packages/core/session；packages/core/agent-loop。

06. Profile / Bundle / Preset：三个“组合层”解决的是三个不同产品问题

层回答的问题生命周期例子
Profile“这个应用形态是什么？”进程 / 产品 surfaceweb, headless, sdk, acp, sdk-minimal
Bundle“这个 profile 装哪些能力集合？”部署 / 安装dsh-base, web-app, 外部 bundle
Agent Preset“这个 session 里的 agent 能做什么？”每 agent / session工具、persona、prompt、compaction policy
这三个层次不要合并成一个“config system”来理解。

为什么这是产品需求而不是技术偏好？ 因为“Web 和 SDK 不同”与“Research Agent 和 Coding Agent 不同”是两种完全不同的差异。前者属于产品入口，后者属于 session 能力。如果混在一起，你会得到大量 if (web && coding) 式组合爆炸。

过度设计风险：如果你的产品只有一个入口、一个 agent 类型、没有第三方扩展，那么 Profile + Bundle + Preset 三层全上没有必要。先保留两层：deployment config + per-agent config，等真实需求出现再拆。

Source: docs/architecture.zh.md；packages/boot/app-boot/README.zh.md；agent preset architecture notes / preset packages。

07. Session / Persistence / Compaction：这是 DSH 最有长期价值的一组设计

Agent 产品的状态不是“聊天记录”。至少有三类：模型可见历史、运行控制状态、外部世界状态。DSH 的核心选择是把可恢复的内部事实写成 append-only SessionEvent，再从中派生模型历史与各种 projection。

一个 durable source，多种 projection。注意：外部文件/命令副作用不因此自动可回滚。

为什么 Compaction 也属于产品架构？

长会话必然碰到 context window 与成本。DSH 没有把 compaction 写死在 loop，而是做成能力 seam：token meter 测量压力，compaction backend 决定怎么缩减，tool-result pruner 先处理大结果。成功压缩替换的是模型派生视图，原始事件仍保留。

值得学：“存储完整事实”和“给模型多少上下文”是两个问题。不要为了节省 token 直接破坏审计历史。
不要误解：event sourcing 不等于 exactly-once side effects。命令、网络请求、外部数据库仍然需要各自的 idempotency / reconciliation 策略。

Source: packages/core/session/README.zh.md；docs/architecture.zh.md；session-persistence；compaction packages。

08. 权限与安全：产品必须先定义“用户愿意把什么权力交给 agent”

DSH 的 SAFETY 文档明确说它尚未经过安全审计，sandbox / approval 只能降低风险，不能保证隔离。这一点反而很适合作为产品设计起点：权限模型不是安全营销，而是用户与 agent 的权力契约。

“用户选择一个权限档位”与“底层如何真正执行限制”应该分层。

产品上必须先回答：默认 read-only 还是 workspace-write？无人值守任务遇到 ask 怎么办？网络、credentials、host plugins 是否与 workspace sandbox 同一信任级？DSH 的插件管理器甚至明确说明 Host plugin code 在宿主进程运行，不受 workspace sandbox 约束。

对你自己的项目：先设计 permission matrix，再写工具。工具写完后再补 approval，通常会出现语义漏洞。

Source: SAFETY.zh.md；permission-presets；sandbox / approval docs；plugin-manager README.zh.md。

09. Plugin / Seam / Cordis：什么时候是必要抽象，什么时候只是平台工程

DSH 的开发规则明确要求“新行为走 plugin / extension point，不优先改 agent-loop”；能力 seam 必须有 Service Definition / Provider / Consumer 三个角色。这对一个要长期扩展的 harness 很合理。

机制解决的真实问题什么时候值得什么时候先别做
Dependency Injection / Service消费者不绑定具体实现至少有 2 个 provider，或明确会 remote/sandbox永远只有一个实现
Typed events / waterfall多个独立模块观察或拦截流程policy、telemetry、approval、retry 都要插入只有一个调用者和一个实现
Reversible effects / Fiberreload/unload 后清理监听器和资源支持 HMR、插件启停、动态组合进程一次启动到退出，组件固定
Bundle / plugin manager第三方分发与部署组合明确做生态或多团队平台单团队内部项目
Runtime invariants跨组件关系在运行中不能悄悄漂移状态复杂、插件多、长期维护纯函数关系用单测就够
判断抽象是否“炫技”的一个好问题：删掉它以后，哪一个用户场景会立刻变差？如果回答只能是“代码没那么优雅”，先不要加；如果回答是“SDK 与 Web 会分叉”“远端执行要改十个工具”“插件卸载会泄漏”，它就在支付真实产品成本。

一个很好的边界：Host plane vs Agent plane

当前 DSH 已经经历过“把太多东西塞进 per-session preset”的反例：有些 registry 被 Host 跨 session 消费，不能移动到 agent-local scope。这个经验很重要：作用域不是为了漂亮，而是由谁需要共享该状态决定。

Source: AGENTS.md；docs/architecture.zh.md；agent preset architecture notes；Cordis primer。

10. 哪些是必要的，哪些是未来空间，哪些可能是炫技？

下面不是对代码质量打分，而是从“如果你自己做产品，什么时候应该付这笔复杂度”的角度分类。

设计分类理由你应该学什么
Turn / Step / Tool lifecycle核心必要任何可执行 agent 都需要清楚的运行状态机先定义语义，再写 loop
Session durable log + resume核心必要长任务与故障恢复直接需要任务寿命大于进程寿命时尽早设计
Sandbox + approval separation核心必要一个是 enforcement，一个是 human policy不要把“问用户”当安全边界
Runtime / surface separation核心必要多入口产品否则必然分叉Web/SDK 不拥有业务逻辑
Compaction seam很快必要长会话必然遇到 context pressure完整历史与模型工作集分开
Agent presets / per-session scope产品驱动多 agent persona/工具集才需要先证明存在多个稳定 archetype
Provider seams everywhere平台驱动有多个 backend 时非常值；否则增加间接层第二个实现出现前可先保留简单接口
Plugin marketplace-style install未来空间这是生态投资，不是 agent 核心有外部开发者后再付供应链成本
大量 invariant companions / verify gates规模化投资几百 package 下合理，小项目会重先给最贵的不变量加检查
“一切皆插件”做到极致可能过度统一性很强，但阅读与组合成本高学原则，不必复制粒度
非常细的 package 拆分可能过度利于 ownership/gates/publish，但认知负担大单团队项目可用模块边界替代 package 边界
不要问“这个 pattern 好不好”；问“在我的产品阶段，边际收益是否高于认知与维护成本”。

11. 你经常用 AI 辅助开发：这会改变架构设计方法

AI 能显著降低“写 boilerplate”的成本，但不会降低错误边界、隐式状态和不清楚 ownership 的成本。甚至相反：agent 越能快速改很多文件，越需要让架构规则机器可读。

AI 时代更值得做

显式 contract：typed service、schema、event discriminant、错误码。

机械 gate：lint / dependency policy / generated catalog / tests。

局部 ownership：一个 package/module 对自己的状态和 teardown 负责。

可搜索的决策记录：让 agent 能找到“为什么”。

AI 时代更危险

过度抽象：AI 很容易生成一套“看起来专业”的层次，却没有用户需求。

隐式魔法：agent 修改局部代码时不知道远端副作用。

规则只写在人脑里：AI 不会自动知道团队约定。

一次生成大架构：缺少真实 failure feedback。

推荐你采用的 AI 开发循环

1. Product brief: 谁用？Job 是什么？哪些失败不可接受？
2. Architecture decision: 只写本次需要的 invariants / boundaries
3. Ask agent to inspect existing code before proposing changes
4. Plan must name: owner, state, lifecycle, failure semantics, tests
5. Implement small vertical slice
6. Add mechanical check for the expensive rule
7. Observe real usage; only then extract a reusable seam
DSH 最值得你借鉴的不是 package 数量，而是 AGENTS.md 这种“把架构规则写给 coding agent 看”的做法。 例如：model-visible 必须 logged、新行为优先 plugin、capability seam 的角色必须完整、配置错误尽早失败。这些规则既服务人，也服务 AI coder。

12. 学习 DSH 源码的顺序：从产品路径进入，不从目录树进入

阶段先回答的问题建议读的源码/文档不要先陷进去
1. 产品面有哪些 surface？用户如何启动？README、user guide、app-boot、profilesvendor/cordis 内部
2. 单轮执行一个 prompt 到 tool result 怎么流动？docs/architecture → turn flow；agent-loop；tools所有 provider
3. 状态什么必须跨进程？如何恢复？session、persistence、checkpoint、resumeUI projection 细节
4. 权限副作用前谁有决定权？sandbox、approval、permission presets、fs/shell平台特定 sandbox 实现
5. 组合App 差异和 Agent 差异分别在哪？profile/bundle/preset/scopeHMR 边角
6. 长任务上下文、后台任务、subagent 怎么管理？compaction、jobs、subagent、goal、schedule实验性 teams
7. 平台化第三方怎么扩展、怎么防腐化？plugin-manager、AGENTS.md、verify scripts、invariants先别复制全部 gate
8. Framework为什么 lifecycle / scope 能成立？Cordis primer → vendor/cordis fiber/events一开始就读 framework internals

你每读一个 subsystem，都用这 8 个问题做笔记

1. User: 谁直接需要它？
2. Job: 用户想完成什么？
3. Trigger: 它什么时候发生？
4. State: 谁拥有状态？状态活多久？
5. Side effect: 它会改变什么外部东西？
6. Failure: 中途失败、取消、重启后是什么语义？
7. Boundary: 为什么需要一个 seam / event / service？
8. Cost: 如果删掉这层抽象，今天哪个真实场景会变差？
建议第一个源码练习：不要“读完整个 DSH”。选一条真实 journey——例如 Web 用户让 agent 修改一个文件——从 UI/Remote 一路追到 inbox → agent-loop → tool-fs → sandbox/approval → SessionEvent → persistence。第二遍再追“进程在 tool 后崩溃并 resume”。这两条路径能覆盖项目最重要的 60% 思想。
